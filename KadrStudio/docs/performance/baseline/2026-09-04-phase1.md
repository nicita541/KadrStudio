Raw BGRA bandwidth at 4K60 is 1,990,656,000 bytes/s. The 4K60 run copied 8.40 GiB in total. Despite their legacy names, `PipeWriteTimeMs` measures only the small control-header writes and `PipeReadTimeMs` includes time blocked waiting for control packets; neither measures MMF payload transfer. The current counters do not split MMF write/read, large-object-heap allocation, WPF render cost, FFmpeg decode, hardware download, pixel conversion, and redirected-stdout transfer into independent timings; Phase 2 must add or use narrower measurements before changing the implementation.

### Initial conclusion

MediaHost receives raw BGRA from FFmpeg at only about 17–18 frames/s, before it can offer those frames to the MMF ring. The primary limiter is therefore upstream of the Desktop reader. The Phase 1 counters do not directly time MMF payload copies, so they are not sufficient on their own to exclude a secondary MMF cost. The unresolved upstream cost includes some combination of HEVC decode, GPU-to-system-memory download, format conversion, the FFmpeg filter graph, FFmpeg rawvideo output, redirected stdout, and the managed full-frame read/copy. The NVDEC utilization samples prove that the GPU video engine is active, but the current `ffmpeg-cuda` / `cuda-requested` diagnostics do not prove the selected decoder, hardware pixel format, or absence of software fallback.

## Full Analysis baseline

Representative source:

`F:\KadrStudio\KadrStudioAiServer\.kadr-ai\data\performance-audit\representative-120s-hevc.mkv`

Characteristics: 120.286 s, 1920x1080, HEVC Main 10, 24000/1001 fps, two AAC audio streams, 15,365,041 bytes.

The current cold path starts FFmpeg once for the full visual proxy transcode and once for each audio stream. With this source that is three FFmpeg launches. The video-understanding worker then opens the visual proxy once and sequentially decodes every proxy frame. Consequently, a cold Full Analysis performs at least two full video decode passes: source to proxy, then proxy through OpenCV. A warm proxy-cache run still performs the OpenCV pass. Every video evidence-gap retry calls analysis again and adds another full proxy sequential pass.

## Planner / Critic VRAM baseline

The Director request used the real structured-reasoning endpoint, Python worker, model lifecycle, and 30B GGUF model with `requireProduction=false`; this bypassed only the stale production identity manifest check.

| Point in lifecycle | GPU memory |
| --- | ---: |
| Before request | about 1,252 MiB |
| Model loading | about 5,706 MiB |
| Inference plateau | about 6,330–6,466 MiB |
| Stage finished | 6,462 MiB |
| Five seconds idle | 6,431 MiB |
| Immediately after `/v2/accelerator/release` | 1,233 MiB |
| Five seconds after release | 1,242 MiB |

The request completed with HTTP 200 after about 95 seconds. The llama-server working set reached about 15,256.5 MiB because only part of the model is GPU-offloaded. The model intentionally remains cached after a successful stage; explicit release terminates the worker/model process and frees about 5.2 GiB of VRAM.

The gateway serializes accelerator work and evicts a different accelerator worker before starting the next analyzer, so its current design does not intentionally keep different heavy analyzer processes resident at the same time. Cancellation removes the runtime. A non-cancellation exception can retain the cached runtime and requires explicit Phase 5 testing.

Critic could not be measured independently: the real endpoint returned HTTP 503 `model_not_qualified` because `Qwen/Qwen3-30B-A3B-Instruct-2507` is not approved for the `Critic` role in the current manifest. Planner-to-Critic, Critic cancellation, and Critic exception timelines are therefore **BLOCKED by model qualification**, not reported as passing.
