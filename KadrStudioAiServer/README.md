# KadrStudio AI Server

Самостоятельный HTTP/CUDA-сервер для KadrStudio. Он владеет API v2, Python workers,
моделями, runtime, AI-кэшами и бинарными артефактами. Desktop-приложение обращается
к нему только по HTTP и не запускает модели или Python локально.

## Запуск

```powershell
.\scripts\install-ai-server-local.ps1
.\scripts\setup-ai-workers.ps1 -InstallDependencies
.\scripts\install-production-models.ps1
.\scripts\run-ai-server.ps1
.\scripts\test-ai-server-connection.ps1
```

Runtime и веса находятся в `.kadr-ai` внутри этой папки и никогда не добавляются
в Git. Конфигурация endpoint и Bearer key описана в `docs/REMOTE_AI_SERVER.md`.

## Диагностика хранения задач

HTTP v2 jobs принимают необязательные `ownerId` и `requestId` (оба вместе).
Активные jobs переиспользуются внутри owner; успешно завершённые результаты —
между owners. Повтор request ID для сохранённого owned job возвращает тот же job,
включая terminal state; другой набор входов с тем же ID отвергается. Дополнительные
request IDs при active dedup сохраняются в записи (не более 128 на job).
DELETE `/v2/jobs/{id}?ownerId=...` требует совпадения owner для активной задачи.
Ответ содержит `ownerId` и `ownershipProtocolVersion: 1`; новый Desktop проверяет
подтверждение, прежде чем считать активную задачу своей. Legacy запросы без owner
сохраняют прежний маршрут, но не объединяются с активными owned jobs.
Owner — идентификатор задачи, не отдельная учётная запись: Bearer-авторизация
остаётся обязательной по существующей политике сервера.

Это ещё не полный distributed resume: Desktop пока создаёт owner на проход анализа,
не восстанавливает его из checkpoint; потеря ответа на создание и авария до durable
commit требуют дальнейшей реализации. Глобальный cache hit не передаёт владение
завершённым job новому owner. Удаление истории ограничивает срок действия dedup.

`GET /health/ready` включает объект `jobStorage`: завершение начального восстановления,
ожидание повторного сканирования, число ожидающих чтений и записей, число задач
с ошибкой хранения. `isHealthy: false` делает readiness ответом HTTP 503, даже если
проверки моделей проходят. После успешного повтора операций статус восстанавливается;
непройденная квалификация моделей остаётся отдельной причиной HTTP 503.
`/health/live` продолжает отвечать на запросы с необходимой авторизацией.

Это состояние наблюдаемых операций, без пробной записи при каждом HTTP-запросе.
Оно не подтверждает устойчивость к отключению питания или отсутствие ещё не
обнаруженных ошибок диска. Неподтверждённые переходы задач пока хранятся в памяти;
авария сервера до их записи остаётся незакрытым риском восстановления.
